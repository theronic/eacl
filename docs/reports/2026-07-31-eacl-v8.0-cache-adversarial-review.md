# EACL v8.0 candidate — adversarial correctness & performance review

**Date:** 2026-07-31
**Branch / PR:** `codex/intelligent-eacl-cache` @ `8195d2f` — [PR #80](https://github.com/theronic/eacl/pull/80)
**Scope:** entire source tree, with emphasis on the v8.0 additions: `eacl.datomic.cache`,
`eacl.datomic.consistency`, `eacl.datomic.integrity`, the cache/consistency plumbing in
`eacl.datomic.core`, and the recursive continuation/page cache in `eacl.datomic.impl.indexed`.
**Baseline:** the full non-benchmark suite was green on this branch when the review was written
(166 tests / 4516 assertions, 0 failures, 0 errors). Every finding below was therefore *not*
covered by the tests as they stood.

> **Status: all findings resolved in this branch.** See [Resolution](#resolution) at the end for
> what changed, the measured before/after, and where each regression test lives. The suite is now
> 179 tests / 6335 assertions, and every regression test fails against the pre-fix source.

## Executive summary

v8.0 is a large, carefully-argued change and most of its hard parts hold up. The live-result
dependency proof is sound within its documented contract (no stale `true` observed under
concurrent grant/revoke), invalidation on `delete-object!`, `write-schema!` and counts is correct,
acyclic pagination survived a 250-iteration randomized cursor fuzz with zero divergence between a
cached and a cache-disabled client, and the Zed-token envelope is properly domain-separated and
constant-time compared.

However there is **one critical correctness bug** that silently returns the wrong page from
`lookup-resources`/`lookup-subjects` **on the default configuration**, plus several
high-severity availability and performance problems — three of which make the cache actively
worse than not having it.

| # | Severity | Finding | Affects |
|---|----------|---------|---------|
| **C1** | **Critical** | Recursive page cache key omits the page direction; a `:last/:before` page is served to a later `:first/:after` request | default config, any recursive permission |
| **H1** | High | A failed *pre-transaction* write (`:create` conflict, unknown object id) increments `:uncertain` and flushes the **entire** live cache | `:live-results? true` |
| **H2** | High | A client constructed before the DB was schema-stamped mints page-1 tokens it then permanently rejects on page 2 | all configs |
| **H3** | High | One result entity without an external id turns the whole lookup page into a thrown `:eacl.consistency/snapshot-unavailable` | all configs |
| **H4** | High (perf) | `delete-object!` holds the coordinator write barrier across *N* Datomic transactions, stalling every `lookup-*` in the process (measured 277 ms) | default config |
| **M1** | Medium | `:exact-results? true` is write-only: `fully-consistent` never reads the exact cache, so the default mode pays 100 % of the write cost for 0 % hit rate | `:exact-results? true` |
| **M2** | Medium | `StackOverflowError` escapes `decrypt-page-token`; page tokens have no length bound and are EDN-parsed before authentication | all configs |
| **M3** | Medium (perf) | The cache does not scale: `can?` with `:live-results? true` measured up to **2.7× slower** than `:cache false` at 8 threads, with negative scaling 1→8 threads | `:live-results? true` |
| **M4** | Low-Med | Every cursor page writes a live-cache entry that is unreachable by construction | `:live-results? true` |
| **L1–L6** | Low | Dead code, inconsistent error typing, asymmetric reverse-rule filtering, config-dependent result shape, hash-keyed admission, hard-failing recursive counts | — |

## Methodology

All findings were reproduced against this branch in a REPL with in-memory Datomic
(`eacl.datomic.datomic-helpers/with-mem-conn`), comparing a cache-enabled client against a
`{:cache false}` client sharing the same `:page-token-key`. Benchmarks: Apple M3 Pro (12 cores),
Temurin JDK 24.0.1, `datomic:mem://`, warmed, `System/gc` between phases. In-memory numbers
*understate* the write-barrier findings, because a real transactor adds network and durable-storage
latency inside the barrier.

## C1 — CRITICAL: recursive page cache serves a backward page to a forward request

**Files:** `src/eacl/datomic/impl/indexed.clj:941` (`recursive-page-request-key`),
`:945` (`cached-recursive-request-page`), `:976` (`store-recursive-page!`),
call sites `:1386-1391`, `:1429-1430`, `:1447-1448`, `:1749-1754`, `:1792-1793`, `:1808-1809`.

### The defect

```clojure
(defn- recursive-page-request-key
  [direction result-kind bound size]
  [:request direction result-kind bound size])
```

`direction` here is the **traversal** direction (`:forward` for `lookup-resources`, `:reverse` for
`lookup-subjects`) — a constant per API, *not* the page direction. The page direction
(`:asc` from `:first/:after` vs `:desc` from `:last/:before`) never enters the key.

`store-recursive-page!` is called from **both** branches:

```clojure
:asc  (... page-stored? (store-recursive-page! continuation-cache :forward :resource bound size page))
:desc (... (store-recursive-page! continuation-cache :forward :resource bound size page))
```

but `cached-recursive-request-page` is only read on the `:asc` branch. So a page produced for
`{:last N :before C}` is written under exactly the key that a subsequent `{:first N :after C}`
reads, and `internal-page?` happily validates it — it *is* a well-formed page, just the wrong one.

### Reproduction (default `:cache` configuration — no cache options at all)

```clojure
;; schema: definition folder { relation owner: user
;;                             relation parent: folder
;;                             permission view = owner + parent->view }   ;; recursive
(def q {:subject (spice-object :user "alice") :permission :view :resource/type :folder})

(def p1 (eacl/lookup-resources client (assoc q :first 3)))       ;; => f0 f1 f2
(def c2 (get-in p1 [:page-info :end-cursor]))                    ;; ordinal 2

(eacl/lookup-resources client (assoc q :last 3 :before c2))      ;; => f0 f1   (correct)
(eacl/lookup-resources client (assoc q :first 3 :after c2))      ;; => f0 f1   (WRONG)
;; the same call on a {:cache false} client => f3 f4 f5
```

Observed on both directions of the API:

| call | cached client | ground truth |
|---|---|---|
| `lookup-resources {:first 3 :after C2}` | `["f0" "f1"]` | `["f3" "f4" "f5"]` |
| `lookup-subjects  {:first 3 :after C2}` | `["u0" "u1"]` | `["u3" "u4" "u5"]` |

The poisoned page also reports **`has-previous-page? false`** — a lie, since it is being served as a
page *after* a cursor.

### Blast radius

A randomized fuzz (20 folders, recursive `view`, 300 random cursor jumps alternating
`:first/:after` and `:last/:before` over page sizes 1–4) produced **89 wrong results out of 300**
against a `{:cache false}` oracle. Failure shapes included:

- wrong offset — `got ["f7" "f8" "f9" "f10"]`, `want ["f12" "f13" "f14" "f15"]`;
- **silent truncation** — `got []`, `want ["f1" "f2" "f3" "f4"]`. An empty page with
  `has-next-page? false` makes a paginating caller stop early and conclude the subject has access
  to fewer resources than it does.

Root cause confirmed by neutralizing only that read path:

```clojure
(with-redefs-fn {#'eacl.datomic.impl.indexed/cached-recursive-request-page (fn [& _] nil)}
  #(probe/fuzz 42 300))
;; => {:failure-count 0}      ;; was 89
```

The same fuzz over an **acyclic** permission graph (`owner + team->access + grp->access`, 250
jumps × 6 page sizes, both directions) reports 0 failures, confirming the defect is isolated to the
recursive page cache.

### Why it is reachable in production

- It needs **no cache configuration** — `normalize-cache-config` treats a missing `:cache` key as
  enabled (`enabled? (not (false? cache-option))`), so every default client has a `LocalStore`.
- The trigger is an ordinary "Previous, then Next" UI flow, or any client that uses a page's
  `end-cursor` as a `:before` bound.
- The page cache is **not** guarded by `:opaque-cache-token` (unlike continuations), so with a
  shared store one process's `:desc` page poisons another process's `:asc` request.
- It is not a privilege escalation: the returned rows are genuine results of the same query at the
  wrong offset. The damage is silent omission/duplication in authorization enumerations.

### Recommended fix

Thread the page direction into the key, and add it to `store-recursive-page!`:

```clojure
(defn- recursive-page-request-key
  [direction result-kind page-direction bound size]
  [:request direction result-kind page-direction bound size])

(defn- store-recursive-page!
  [continuation-cache direction result-kind page-direction bound size page]
  ...
  (put-page! (recursive-page-request-key direction result-kind page-direction bound size) page weight)
  ...)
```

Minimal alternative: pass `page-direction` and skip the `:request` write entirely when it is
`:desc` — backward reuse is already served by `recursive-page-end-key`, which *is* sound. That key
is `[:end direction result-kind end-ordinal size]`, and cross-direction reuse there is legitimate:
a page ending at ordinal *k* with size *N* covers ordinals *k−N+1…k* whichever way it was produced,
and an `:asc` page can only be short when it is the final page — in which case no `:before` cursor
past it exists. The fuzz above issued ~150 `:desc` requests and found zero divergence on that path.

Whichever fix is taken, both key builders deserve an explicit comment that `direction` is the
*traversal* axis, not the page axis. That naming collision is what made this bug invisible — the
key looks direction-scoped, and is not.

### Regression test to add

```clojure
(deftest recursive-page-cache-is-direction-scoped
  ;; page 1 -> backward from its end-cursor -> forward from the SAME cursor
  ;; must equal the {:cache false} answer, for both lookup-resources and lookup-subjects.
  )
```

## H1 — A failed pre-transaction write flushes the entire live cache

**Files:** `src/eacl/datomic/cache.clj:348-385` (`with-mutation`),
`src/eacl/datomic/core.clj:876-895` (`spiceomic-write-relationships!`).

`with-mutation` fails closed on any exception from `f`:

```clojure
(catch Exception e
  ;; A helper failure could occur after its Datomic transaction
  ;; committed but before its changed relation ids were returned.
  ;; Fail closed by making every prior live result unreachable.
  (swap! generation-state update :uncertain unchecked-inc)
  (throw e))
```

The intent — a *post-commit* failure — is right. But `f` is the whole of
`spiceomic-write-relationships!`, including endpoint resolution and conflict detection, which run
**before** `d/transact`. `:uncertain` is part of every `dependency-generation` proof, so bumping it
makes 100 % of live entries — for every query, every permission, every subject — unreachable.

Two of the most routine application-level errors in EACL trigger it:

```clojure
(eacl/create-relationship! client existing-rel)   ;; :eacl/relationship-conflict  (impl.clj:693)
(eacl/create-relationship! client typo-rel)       ;; :eacl/unknown-object         (core.clj:829)
```

Measured:

```clojure
{:gen-before {:incarnation "7b22b77b-…" :uncertain 0 :revision 1008}
 :gen-after  {:incarnation "7b22b77b-…" :uncertain 2 :revision 1008}
 :cache-flushed? true
 :calls-before 1 :calls-after 2}   ;; the next can? recomputed
```

Nothing was committed; the database is unchanged; the entire cache is gone. `:create` conflicts are
*expected* (that is why `:touch` exists), and unknown object ids are user-input-driven — so a
caller who can reach a write endpoint can hold the live cache at a 0 % hit rate indefinitely.

Secondary effect on the **default** config: `:uncertain` also feeds the recursive-continuation
namespace, so a bumped counter makes every stored continuation for a fresh page-1 walk unreachable
(in-flight cursors survive, since they carry their own proof in the token).

**Fix:** only bump `:uncertain` when a transaction may actually have been submitted. Either
(a) hoist resolution/validation out of the barrier and keep only transact + publish inside it, or
(b) have `f` set a `transacted?` flag (or throw a distinguished `:eacl/pre-commit` exception type)
and gate the `unchecked-inc` on it. `impl/validate-relationship-operation!` is already hoisted
above `coordinate-relationship-mutation` — the same treatment for
`spice-relationship->internal` / `tx-update-relationship` is the natural extension.

## H2 — A client built against an unstamped database permanently breaks its own pagination

**Files:** `src/eacl/datomic/core.clj:389-397` (`validate-page-token-schema!`),
`:930-1011` (`capture-result-context`), `src/eacl/datomic/impl/indexed.clj:348-360`
(`make-schema-cache`).

`make-client` latches `(make-schema-cache initial-db)` once. If the database has no
`:eacl/schema-version` yet, `client-schema-version` is `nil` **for that client's whole life** — it
only rotates via `write-schema!` *through that client*.

- **Page 1** takes the live branch: `:schema-version (client-schema-version opts)` → `nil`, and the
  page token is minted with `:schema-version nil`.
- **Page 2** takes the historical branch and re-derives the version from the `d/as-of` DB:
  `:schema-version (some-> schema-cache :schema-version str)` → the **real, non-nil** stamp.
- `validate-page-token-schema!` compares them and throws.

Reproduction:

```clojure
(def early (core/make-client conn {}))          ;; process start-up, DB not yet stamped
(def admin (core/make-client conn {}))
(eacl/write-schema! admin simple-schema)        ;; schema written by a DIFFERENT client
…
(eacl/lookup-resources early (assoc q :first 2))                       ;; => ["a0" "a1"]  ✅
(eacl/lookup-resources early (assoc q :first 2 :after end-cursor))     ;; ❌
;; {:type :eacl.pagination/stale-schema
;;  :expected "6a6cb33b-4e82-419e-bc82-eee9e0bc72f4", :actual nil}
```

`read-relationships` fails identically. `can?` and single-page lookups keep working, so the failure
is invisible until the first paginated read — and it never heals.

This is the exact shape of a real deployment: a service constructs its EACL client at boot, and
the schema is written by a migration job, a sibling process, or a later request. The README
promises only that such a database "remains uncached until its first `write-schema!`" — in fact
**pagination is broken, not merely uncached**.

**Fix options** (either, or both):

1. In `capture-result-context`'s historical branch, keep the client's `nil` generation when the
   client is unstamped rather than adopting the historical stamp — i.e. make the token's
   `:schema-version` and the validator's expectation come from the same source.
2. Let `make-client` re-read `:eacl/schema-version` lazily (once) when its latched version is
   `nil`, promoting the client to a stamped generation the first time it observes a stamp. This
   preserves the "one read per generation" invariant for the normal case while removing the
   permanent-`nil` trap.

At minimum, `validate-page-token-schema!` should not reject `nil → non-nil`; that transition means
"the client was unstamped when it minted the cursor", which is reconstructable, not stale.

## H3 — A single entity without an external id turns the whole lookup page into a hard error

**File:** `src/eacl/datomic/core.clj:435-453` (`coerce-lookup-page`). New in v8.0 — v7.3 emitted
`(spice-object type nil)`.

```clojure
(let [external-id ((:entid->object-id opts) db id)]
  (when (nil? external-id)
    (snapshot-unavailable! {:operation op :revision basis-t :entity-id id}))
  (spice-object type external-id))
```

Reproduction — a consumer retracts an entity without calling `delete-relationships!` first
(the exact hazard `eacl.datomic.integrity/dangling-relationship-report` exists to detect):

```clojure
@(d/transact conn [[:db/retract acct2-eid :eacl/id "acct2"]])

(eacl/can?             client alice :admin acct1) ;; => true                      ✅
(eacl/count-resources  client q)                  ;; => {:count 2 :limit -1}       (counts the ghost)
(eacl/read-relationships client {:subject/id "alice"})
;;   => [["alice" :owner "acct1"] ["alice" :owner nil]]                            (silent nil)
(eacl/lookup-resources client q)
;;   => THROWS {:type :eacl.consistency/snapshot-unavailable
;;              :operation :lookup-resources :revision 1011 :entity-id 17592186045424}
;;      "The requested EACL cache snapshot is unavailable."
```

Three problems:

1. **Availability.** One dangling entity poisons every page it lands on, and the caller cannot page
   past it — `lookup-resources` becomes permanently unavailable for that subject until the data is
   repaired. Neither `can?` nor `count-resources` fails, so the APIs disagree.
2. **Misleading diagnosis.** The error says the *cache snapshot* is unavailable and reports a
   `:revision`. Caching is irrelevant here — it fires with `{:cache false}` too. An operator will
   chase the cache; the actual cause is a missing `:eacl/id`.
3. **Doc contradiction.** README:614 says "Missing external IDs return the ordinary false/empty
   boundary result and are not cached", and :616 says deleting the live entity "does not turn an
   otherwise valid cached snapshot into a boundary error". For *result* entities on a
   `fully-consistent` read, the code does exactly the opposite.

**Fix:** distinguish the two cases. A cached *historical* answer whose EIDs no longer resolve at
that basis is genuinely a snapshot problem. A **live** read whose result entity has no external id
is a data-integrity problem: give it its own error type (e.g. `:eacl/unresolvable-object` with the
offending eids), or — probably better for availability — skip the entity and surface it in
`:page-info`, so one bad row cannot deny the whole enumeration. Either way, align the README.

## H4 — `delete-object!` stalls every lookup in the process

**Files:** `src/eacl/datomic/core.clj:1022-1066` (`spiceomic-delete-object!`),
`:870-874` (`coordinate-relationship-mutation`), `src/eacl/datomic/cache.clj:348-385`
(`with-mutation`), `src/eacl/datomic/core.clj:974-1011` (`capture-result-context`).

`spiceomic-delete-object!` runs its **entire batch loop** — `(partition-all 1000 tx-data)`,
one `@(d/transact …)` per batch — inside `cache/with-mutation`, i.e. holding the coordinator's
`ReentrantReadWriteLock` **write** lock. Meanwhile `lookup-resources`/`lookup-subjects` call
`capture-result-context` with `coordinate?` hardcoded `true`, so every one of them takes the
coordinator **read** lock.

Because the cache is enabled by default, a coordinator always exists, so this applies to the
**default configuration**, where it buys nothing (live results are off by default).

Measured (in-memory Datomic, no network):

| workload | result |
|---|---|
| `delete-object!` on a subject with 20 000 relationships | 270 ms, 40 transactions |
| concurrent `lookup-resources {:first 10}` median latency | **6.8 ms** |
| concurrent `lookup-resources {:first 10}` max latency | **277 ms** |

The reader is blocked for essentially the whole delete window. Against a real transactor those 40
round trips are seconds, not milliseconds, and *every* `lookup-*` in the JVM waits.

A smaller version of the same problem applies to `write-relationships!`, which holds the write lock
across a single `d/transact` — so ordinary relationship writes serialize all lookups for one
transactor round trip each.

**Recommendations:**

1. Take the barrier **per batch** in `delete-object!`, not once around the loop; publish each
   batch's `basis-t`/changed relations as it commits. Correctness is preserved: the proof only has
   to be monotone, and a partially-deleted object is already observable to readers between batches
   today (the batches are separate transactions regardless).
2. Do not take the coordinator read barrier when `:live-results? false`. `lookup-resources`
   (`core.clj:1131-1133`) and `lookup-subjects` (`:1245-1247`) pass `coordinate?` as a hard-coded
   `true`, whereas `can?` (`:1086-1088`), `count-resources` (`:1205-1207`) and `count-subjects`
   (`:1308-1310`) all pass `(:cache-live-results? opts)`. With live reuse off, the proof is only
   used to namespace continuations and page tokens; a slightly conservative proof costs a cache
   miss, not correctness. Make the two lookups consistent with the other three — or capture the
   proof without the lock and re-validate it.
3. Bound the retry loop at `core.clj:1003-1010`. `(loop [] … (await-revision-db …) (recur))` has no
   iteration or deadline cap; under sustained write load a reader can bounce indefinitely, each
   iteration paying a `d/sync`. A bounded retry that surfaces
   `:eacl.consistency/freshness-unavailable` would be consistent with the rest of the module.

## M1 — `:exact-results? true` is write-only for the default consistency mode

**File:** `src/eacl/datomic/core.clj:665-712` (`cached-authorization-result`).

```clojure
hit (case mode
      :fully-consistent  (current-hit)     ;; live key only
      :minimize-latency  (latest-hit nil)
      :at-least-as-fresh (latest-hit requested-t)
      :at-exact-snapshot (exact-hit))
```

With `{:cache {:exact-results? true}}` (and `:live-results?` off, which is the documented way to
"retain completed exact snapshots without live reuse or a relationship coordinator"),
`live?` is false ⇒ `live-key` is nil ⇒ `current-hit` is always nil. So `fully-consistent` — the
**default** mode for every `can?`/`lookup`/`count` — never reads the cache, while
`store-cached-answer!` faithfully writes an exact entry *and* a `:latest-result` pointer on every
call.

Measured: three identical `fully-consistent` `can?` calls at the same basis ⇒ **three** computations.

```clojure
{:fully-consistent-computes-for-3-identical-calls 3
 :after-minimize-latency 3}
```

This is a pure missed hit, and it is safe to fix: `exact-key` is
`[… database-id schema-version op query-identity [:exact basis-t]]`, and two connection-backed DB
values of the same database at the same `basis-t` are *the same value*. Adding `exact-hit` as a
fallback for `:fully-consistent` is sound and turns `:exact-results?` from a pure cost into the
accelerator the README advertises:

```clojure
:fully-consistent (or (current-hit) (exact-hit))
```

Until then, `:exact-results? true` on its own is net-negative: it consumes admission weight and
eviction budget for entries only `at-exact-snapshot`/`minimize-latency` readers can use.

## M2 — `StackOverflowError` escapes page-token decoding; tokens are unbounded and parsed before authentication

**File:** `src/eacl/datomic/core.clj:157-192` (`decrypt-page-token`).

```clojure
(catch clojure.lang.ExceptionInfo e (throw e))
(catch Exception e (throw (ex-info "Invalid page token." {:token token} e)))
```

`eacl.datomic.consistency/token-data` gets this right — it caps length at 4096 and explicitly
catches `StackOverflowError` (`consistency.clj:146-208`). `decrypt-page-token` does neither.

Reproduced: an `:after` value of `eacl3_<base64 of "[[[[…60 000…]]]]">`:

```clojure
{:deeply-nested [:THROWABLE "java.lang.StackOverflowError"]}
```

A `StackOverflowError` propagates out of `lookup-resources` past every `catch Exception` in the
stack. In a typical request-handling stack that means an untyped 500 (or a killed worker) instead
of `:eacl.pagination/invalid-cursor`.

Separately, there is **no length bound**: a 4 MB `:after` string is Base64-decoded (~3 MB) and
EDN-parsed *before* the AES-GCM tag is ever checked. That is unauthenticated CPU and allocation
amplification on a public parameter.

**Fix:**

```clojure
(def ^:private maximum-page-token-length 8192)   ;; or whatever real cursors need + headroom
…
(when-not (and (string? token)
               (<= (count token) maximum-page-token-length)
               (.startsWith ^String token page-token-prefix))
  (throw (ex-info "Invalid page token."
                  {:type :eacl.pagination/invalid-cursor
                   :eacl/error :eacl.pagination/invalid-cursor
                   :reason :malformed})))
…
(catch StackOverflowError _ (invalid-page-token! :malformed))
```

Also: the ex-data currently echoes the whole `:token` back to the caller, and none of the
non-`:database-mismatch` failures in `validate-page-token-identity!` (`core.clj:369-386`) carry a
`:type`/`:eacl/error`, so callers cannot pattern-match cursor failures uniformly. Give them all
`:eacl.pagination/invalid-cursor` and drop the token echo.

## M3 — The cache does not scale; `:live-results? true` is slower than no cache under concurrency

**Files:** `src/eacl/datomic/cache.clj:157-264` (`LocalStore`), `src/eacl/datomic/core.clj:334-349`
(`list-query-shape` / `stable-hash`), `:466-477` (`result-cache-prefix`).

Benchmark: `permission view = owner + team->access`, 200 docs, 20 000 (`can?`) / 3 000 (`lookup`)
ops, 8 threads on 12 cores. Figures are µs/op, aggregate (lower is better), three independent runs:

| operation | `:cache false` | default cache | `:live-results? true` |
|---|---|---|---|
| `can?`, 1 thread | 5.52 / 5.73 / 5.29 | 5.89 / 5.73 / 5.31 | **6.14 / 4.29 / 3.48** |
| `can?`, 8 threads | 2.42 / 1.61 / 1.70 | 1.40 / 1.29 / 1.26 | **3.70 / 4.35 / 4.21** |
| `lookup {:first 20}`, 1 thread | 116 / 101 / 99 | 114 / 110 / 106 | 95 / 99 / 90 |
| `lookup {:first 20}`, 8 threads | 23.1 / 20.5 / 24.3 | 27.7 / 23.7 / 20.7 | 33.7 / 22.1 / 28.3 |

The `lookup` rows are within run-to-run noise and should not be read as a regression. The `can?`
rows are not:

- Single-threaded, live results **help** — 3.5–6.1 µs vs 5.3–5.7 µs uncached.
- At 8 threads they **hurt**, consistently: 3.7–4.4 µs/op with live results vs 1.6–2.4 µs/op
  uncached and 1.3–1.4 µs/op with the default cache — a 1.5–2.7× slowdown versus no cache at all,
  on a 100 % hit-rate workload.
- Worst of all, live `can?` shows **negative scaling**: 3.48 µs/op at 1 thread and 4.21 µs/op
  aggregate at 8 threads, i.e. eight cores deliver roughly the throughput of one.

The isolated store confirms the cause: `safe-entry-value` on a warm key costs 0.70 µs
single-threaded and only reaches 0.44 µs/op aggregate at 8 threads — a ≈1.6× speedup on 8 cores.

Causes, in rough order of impact:

1. **One monitor for the whole store.** `LocalStore` guards every operation with
   `(locking entries …)` on a single `LinkedHashMap`. Access-ordered `LinkedHashMap` mutates on
   `get`, so a lock *is* required — but a striped design, or a proper concurrent LRU
   (Caffeine-style), would remove the serialization. If a dependency is unacceptable, N-way
   striping by `(hash k)` over N sub-maps is a small change with most of the benefit.
2. **A shared metrics atom updated on every hit.** `update-metric` does
   `(update-in state [:by-kind kind metric] (fnil inc 0))` inside the monitor — a contended CAS plus
   several map allocations *per cache read*. Make counters `LongAdder`s (or make metrics opt-in);
   this is the cheapest large win.
3. **The coordinator read barrier on the hot path** — see H4.
4. **Key construction per call.** Every lookup computes `list-query-shape` (canonicalize + `pr-str`
   + SHA-256 + Base64) and `result-cache-prefix` re-canonicalizes the same query. For a query whose
   shape is stable across pages this is recomputed every time. Consider memoizing the shape on the
   normalized query, and reusing the canonical form between the two.

None of this is a correctness issue, but the headline v8.0 feature currently makes the hottest API
slower on multi-core hosts, which is worth fixing (or documenting) before release.

## M4 — Cursor pages write unreachable live-cache entries

**File:** `src/eacl/datomic/core.clj:608-640` (`store-cached-answer!`).

```clojure
(when (and cache-scope (:cache-live-results? opts))
  (cache/safe-store-entry! store namespace (result-cache-key cache-prefix cache-scope) kind answer …))
```

For a cursor page, `capture-result-context` sets `:cache-scope (:cache-scope decoded)` and forces
`:mode :at-exact-snapshot`. The live entry is therefore written under a prefix whose
`query-identity` contains an `:after`/`:before` edge — and any request carrying such an edge decodes
a token, takes the historical branch, and is forced to `:at-exact-snapshot`, which reads `exact-key`,
never the live key. The entry can never be read.

Measured on a 2-page walk with `:live-results? true`:

```clojure
{:by-kind {:lookup-page {:puts 4} :latest-result {:puts 2}} :puts 6}
```

Three entries per page, of which one per cursor page is dead weight competing for the same
`:max-weight`/`:max-entries` budget. The `:latest-result` pointer for a cursor prefix is likewise
unreachable.

**Fix:** skip the live-key and `:latest-result` writes when the answer came from the historical
branch (e.g. `(when (and cache-scope (:cache-live-results? opts) (not= :at-exact-snapshot mode)) …)`,
or thread an explicit `:historical? true` through `consistency-context`).

## Lower-severity findings

**L1 — Dead code paths.** `:required? true` and `:exact-only?` are read
(`impl/indexed.clj:906`, `:1394`, `:1757`) but never set to a truthy value by any producer —
`recursive-continuation-context` hard-codes `{:required? false …}` (`core.clj:734`) and never sets
`:exact-only?`. `exact-recursive-page-unavailable!` (`:998`) is therefore unreachable. Either wire
them to a real option or delete them; unreachable failure branches rot.

**L2 — `read-relationships` validates the token schema after the empty-page short-circuit.**
`core.clj:805-818`: a filter naming a non-existent object returns `empty-page` *before*
`validate-page-token-schema!`, so a cursor from a different schema generation yields an empty page
instead of the typed `:eacl.pagination/stale-schema` that `lookup-resources` raises
(`core.clj:1139`). Make the ordering uniform.

**L3 — Asymmetric subject-type filtering in reverse traversal.**
`forward-seed-state` skips `:arrow-relation` rules whose `:target-subject-type` doesn't match the
query subject type (`impl/indexed.clj:1159`), but `reverse-goal-rule-work`'s `:arrow-relation`
branch (`:1505-1524`) has no equivalent guard — it issues a `resource->subjects` scan with a
relation eid whose declared subject type cannot match, which is always empty. Correct, but a wasted
index seek per intermediate on multi-subject-type schemas. Add the same
`(= (:subject-type state) (:target-subject-type rule))` guard.

**L4 — Result shape depends on cache configuration.** `store-cached-answer!` runs `portable-result`,
so with caching on, `:lookup-page` results are plain `{:type :id}` maps; with
`{:cache false}` (or when neither live nor exact retention is enabled) the short-circuit at
`core.clj:673` returns `SpiceObject` records. `coerce-lookup-page` handles both, but this is a
latent trap for any future code that relies on record type. Normalize before the branch.

**L5 — Admission counter keyed by hash.** `frequency-admitted?` (`cache.clj:131-143`) tracks
sightings under `[kind (hash k)]`, so colliding keys share a counter and one key's second sighting
can admit a different key's first. Harmless (admission is a heuristic, and `:two-hit-kinds`
defaults to `#{}`), but worth a comment or the full key.

**L6 — Unbounded recursive counts fail hard.** `count-resources` on a traversal permission without
`:count-limit` throws `:eacl.recursive-traversal/limit-exceeded` once `:max-derived-grants`
(default 100 000) is crossed — verified. This is intentional and documented in
`default-recursive-traversal-limits`, but it means "how many things can this user see?" is a
*runtime error* rather than a degraded answer on large tenants. Consider returning
`{:count n :truncated? true :limit :max-derived-grants}` instead of throwing, or make the limit
error carry the partial count.

## What held up under attack

Worth recording, so these are not re-litigated:

- **Live dependency proofs are sound.** `calc-permission-relationship-eids` collects
  `:relation-eid`, `:via-relation-eid` and sub-path relation eids across all reachable permission
  nodes; `relationship-changes` correctly extracts the relation eid from `(nth v 1)` of both tuple
  attributes; `dependency-generation`'s `max` is monotone, so there is no ABA. 300 concurrent
  grant/revoke cycles against a live-cached reader produced **0 stale-`true`** answers.
- **Invalidation is correct** for `delete-object!` (`true → false`, `["d1"] → []`), incremental
  counts (`1 → 2 → 1`), and `write-schema!` rotation (`true → false` when a relation is dropped
  from a permission).
- **Acyclic pagination is correct** under the cache: 250 randomized cursor jumps × 6 page sizes ×
  both directions, cached vs `{:cache false}`, zero divergence; forward walk = backward walk =
  single-page result = `count-resources`.
- **Continuation eviction degrades safely.** With `{:max-weight 8192 :max-entries 1}` (continuations
  constantly evicted), a full recursive walk still returns exactly the uncached result — the
  `d/as-of` replay path works.
- **Database identity is stable.** `(.id ^datomic.Database db)` returns the same string across
  `d/db`, `d/as-of` and `d/filter` values, so page-token database binding is sound.
- **Zed tokens** are properly domain-separated (`derive-signing-key`), length-bounded, compared with
  `MessageDigest/isEqual`, and `token-data` catches `StackOverflowError`. Only the *page* tokens
  lack the equivalent hardening (M2).
- **Cursor + live-change interaction:** page 2+ pins `d/as-of` at the cursor's basis and carries the
  page-1 relationship proof, so relationship or schema churn after page 1 cannot alter later pages.

3. **H1**, **H4** — barrier scoping. H4 also removes most of the default-config overhead.

## Why the suite missed all of this

`differential_test.clj` — the one place that already encodes the right invariant
(`lookup == can?-derived truth == paginated union at several page sizes == count`) — runs entirely
against **raw `eacl.datomic.impl` / `impl.indexed` with a bare `db`**. The cache and the consistency
plumbing live in `eacl.datomic.core`, which that test never enters, so no amount of randomization
there could have found C1.

The single highest-value follow-up is therefore not a test per finding, but **one new differential
test that runs the existing invariants through `core/make-client`**, parameterized over the cache
configurations, with a `{:cache false}` client (sharing the same `:page-token-key`) as the oracle:

```clojure
(doseq [cfg [{:cache false}
             {}                                              ;; default: continuations only
             {:cache {:exact-results? true}}
             {:cache (assoc (cache/local-context) :live-results? true)}
             {:cache {:max-weight 8192 :max-entries 1}}]]     ;; constant eviction
  ;; forward walk, backward walk, random cursor jumps in BOTH directions
  ;; from the same cursor, single-page read, and count must all agree.
  )
```

The "random cursor jumps in both directions from the same cursor" clause is the part that catches
C1; the eviction configuration is the part that proves the `d/as-of` replay path; and running the
same body under `{:cache false}` is what makes every one of these findings a one-line assertion.
Reproduction scripts for each individual finding above are straightforward to port into
`test/eacl/datomic/` alongside it.

### Measured before / after

**C1** — randomized cursor fuzz, 300 jumps alternating direction over a recursive permission:

| | failures |
|---|---|
| before | **89 / 300** |
| after | **0 / 300** |

**H4** — `delete-object!` on a subject with 20 000 relationships, with a concurrent `lookup-resources` loop:

| | delete | reads completed during it | max read latency |
|---|---|---|---|
| before | 270 ms | 13 | **277 ms** |
| after | 339 ms | **2519** | **18.2 ms** |

The delete itself got slightly slower because it now interleaves with 2 500 reads instead of
blocking them — the intended trade.

**M3** — `can?` on `view = owner + team->access`, µs/op aggregate (lower is better):

| | 1 thread | 8 threads | scaling 1→8 |
|---|---|---|---|
| `{:cache false}` | 5.25 | 2.29 | 2.3× |
| before, `:live-results? true` | 3.48 | **4.21** | **0.83× (negative)** |
| after, `:live-results? true` | **4.94** | **1.01** | **4.9×** |

Live `can?` went from ~2.3× *slower* than no cache at 8 threads to ~2.3× *faster*, and the negative
scaling is gone.

`lookup-resources` retains ~10–25 % overhead with live results at 8 threads. That is not the store
failing to hit — 5 identical lookups issue 1 traversal and 4 store hits.

**Correction to an earlier reading of this number.** I first attributed it to boundary
EID→external-ID coercion, which is deliberately never cached. Profiling with the suite's own
`profile-var` instrumentation shows that is wrong: on a fully cached 40-page recursive walk,
`coerce-lookup-page` costs 3.32 ms, of which **`encrypt-page-token` is 2.92 ms (88 %)** and
`d/entity` is 0.10 ms (3 %, at 96.8 ns/call). Adding `decrypt-page-token` (1.07 ms), roughly
**half of a cached page's wall time is page-token serialisation, against 7 % for the authorization
engine itself**.

And the token cost is not cryptography: AES-GCM is ~1.24 µs of a 41 µs
`encrypt-page-token`. The rest is `canonicalize` + `pr-str` + `edn/read-string` — Clojure's printer
and reader — run three to four times per token. A positional `DataOutputStream` encoding of the
same fields measures 0.49 µs encode / 0.59 µs decode, i.e. **~106 µs → ~5 µs per paginated call**.

That is the largest single performance win available in the codebase, it is a pure encoding change
behind a `page-token-version` bump, and it is out of scope for this correctness PR. Caching
external IDs, by contrast, would trade a documented correctness invariant for a 3 % margin and
should not be pursued.

### Note on H3's chosen behaviour

The review offered two options: a typed error, or skipping the row and surfacing it in `:page-info`.
The typed error was chosen. Silently omitting rows from an authorization enumeration is the same
failure class as C1 — the caller cannot tell a shortened list from a real one — and the entity is
genuinely broken. The error now names every offending eid, the likely cause, and the repair tool, so
one pass fixes the data. `read-relationships` still returns dangling halves with a nil id, because
reading them is how you repair them.
