**Date:** 2026-07-28
**Scope:** Full read of `src/` at `b9587f1` (branch `codex/v7.3-cursor-frontiers`, PR #78), plus

(`indexed-test`, `spice-test`, `schema-test`, `config-test`, `parser-test`, `differential-test`,

## Verdict on the v7.3 frontier design

The core algorithm is **sound**. I attacked it with adversarial scenarios at page size 1 and could
not break correctness. What was verified (all at the `eacl.datomic.impl.indexed` level, plus a
token-layer pass through `eacl.datomic.core`):

| Scenario | Result |
|---|---|
| Union (relation + arrow) with intermediate eid order **anti-correlated** to result eid order, forward `:first 1` chain vs. full enumeration | identical |
| Same, backward bare `:last 1` + `:before` chain (desc frontier reuse) | identical, reversed |
| Arrow path exhausting early — `:exhausted` marker carried on later cursors, results stay complete | correct (`["a0"] [:exhausted] [:exhausted] …`) |
| Jump-back: replaying pagination from a page-1 cursor after walking to the end | identical suffix |
| Direction flip: `:asc`-minted cursor used with `:last`/`:before` (frontiers dropped by direction scoping, bound still applies) | correct |
| Nested arrow (`server.admin = account->admin`, `account.admin = owner + platform->super_admin`) both directions | identical |
| `lookup-subjects` reverse frontiers with multiple intermediates and anti-correlated owner eids, both directions | identical |
| Recursive engine (`folder.view = owner + parent->view` with an eid-inverted edge and a diamond): forward walk, `count-resources`, `:last N :before` window, bare-`:last` rejection, stale-cursor detection after a mutating tx | all correct |
| Token layer: TTL expiry, cross-op token, token from another client's keyring | all rejected with the right errors |

Why the design holds: a path frontier records the first intermediate (in scan order for the
frontier's direction) that had *any* result beyond the page-start bound. Intermediates before it had
none beyond that bound, so they can have none beyond any later bound in the same direction at the
same basis. The frontier intermediate itself is rescanned inclusively, so nothing between the old
and new result bound can be skipped. `:exhausted` is the same argument with zero contributors, and
is only sound **at a fixed basis** — which the public API guarantees by pinning `d/as-of basis-t`
inside the encrypted token (see Finding 7 for the raw-impl caveat).

The bugs found below are all *outside* that core algorithm.

### Remediation notes (2026-07-28, same branch)

- **1:** `identifier` grammar now requires a word boundary after reserved words; exact keywords
  remain rejected. Round-trip tests added in `parser-test`.
- **2:** `extract-permissions` throws `:eacl.schema/duplicate-permission`, mirroring the existing
  duplicate-relation check.
- **3:** `impl/read-relationships` validates filters: unknown keys throw
  `:eacl.filters/unknown-filter`; an empty/unanchored filter map throws
  `:eacl.filters/missing-anchor`. The anchor set is `#{:resource/type :subject/type
  :resource/relation :subject/id :resource/id}` — a superset of the docstring's original three,
  since an id-anchored scan is bounded and was always safe. Protocol docs updated.
- **4:** `:resource/id-prefix` (and `:subject/relation`, same class — silently ignored on the
  *non-recursive* `lookup-subjects` path) now throw `:eacl.pagination/unsupported-filter`;
  removed from the protocol docs.
- **6:** rule ids gain the intended `relation-eid` segment. Rule *sort order* is unchanged for all
  live schemas (ids only diverged where they were already distinct), so recursive cursor ordinals
  are unaffected; in-flight cursors are covered by the 5-minute TTL and the stale-cursor guard.
- **7:** impl-level reads resolve string ids via `[:eacl/id …]` (`object-eid`); unresolvable ids
  read as unknown objects (`can?` → false, lookups → empty page). The basis caveat is now stated in
  the README and the `lookup-resources`/`lookup-subjects` docstrings.
- **9:** all read APIs reject non-fully-consistent requests with `:eacl/unsupported-consistency`
  (previously only `can?`); `:consistency` is excluded from the page-token query-shape hash.
  Deploy note: tokens minted *before* this change with `:consistency` in the query fail shape
  validation after deploy — self-healing within the 5-minute TTL.
- **11:** a stamp **newer** than the build's `storage-version` now throws `:eacl/storage-version`.
- Suite after fixes: 73 tests, 1297 assertions, 0 failures (was 65/1243).

## 1. [High] Parser rejects identifiers that start with a reserved word

**Where:** [parser.clj:75](../../src/eacl/spicedb/parser.clj) — the `identifier` rule:

```
identifier = !('nil' | 'self' | 'definition' | 'relation' | 'permission' | 'with' | 'any' | 'all') #'[a-zA-Z_][a-zA-Z0-9_]*'
```

Instaparse's negative lookahead succeeds if the inner literal matches a **prefix** at that position —
there is no word-boundary requirement. Any identifier beginning with one of the eight keywords fails
to parse, and `write-schema!` rejects the whole schema with a parse error.

**Verified repro** (all of these are legal SpiceDB, all fail in EACL):

```clojure
;; :PARSE-FAIL for every one of these
"permission allowed = owner"        ; 'all' prefix
"permission anytime = owner"        ; 'any' prefix
"relation allocation: user"         ; 'all' prefix
"relation relationship: user"       ; 'relation' prefix
"permission without_x = owner"      ; 'with' prefix
"permission selfie = owner"         ; 'self' prefix
"permission nilable = owner"        ; 'nil' prefix
;; :ok — 'definitely' diverges from 'definition' before the end of the keyword
"permission definitely = owner"
```

Real-world names like `allocation`, `all_users`, `any_member`, `withdrawal`, `relationship` are
unusable. SpiceDB's lexer uses maximal-munch tokenization, so these are accepted there — this is a
compatibility break, not just an inconvenience.

**Impact contained to schema writes:** it fails loudly at `write-schema!`, it cannot corrupt stored
data. Severity is High because it blocks legitimate schemas and the failure (an instaparse error at
the identifier position) does not explain *why*.

**Fix:** require a word boundary after the keyword in the lookahead. Simplest is a single regex with
embedded negative lookahead:

```
identifier = #'(?!(?:nil|self|definition|relation|permission|with|any|all)(?![a-zA-Z0-9_]))[a-zA-Z_][a-zA-Z0-9_]*'
```

or keep the instaparse form but guard the keyword with a non-word-char lookahead:
`!(('nil' | … | 'all') #'(?![a-zA-Z0-9_])')`. Add round-trip tests for the list above.

## 2. [Medium] Duplicate `permission` declarations are silently unioned

**Where:** [parser.clj:166-176](../../src/eacl/spicedb/parser.clj) (`extract-permissions`).

The 2026-07-06 audit (finding 9) added duplicate rejection for *definitions* and *relations*
(`extract-relations` throws `:eacl.schema/duplicate-relation`). Permissions were missed:
`extract-permissions` returns a plain seq, so both declarations survive and become two permission
entities with distinct `:eacl/id`s.

**Verified repro:**

```clojure
(->eacl-schema (parse-schema
  "definition user {}
   definition doc { relation owner: user
                    relation editor: user
                    permission view = owner
                    permission view = editor }"))
;; => 2 permission entities; runtime evaluates view = owner + editor
```

Because `find-permission-defs` unions all defs matching `(resource-type, permission-name)`, the
duplicate quietly **broadens access**. A copy-paste error (second line was meant to be a different
permission name) both grants unintended access *and* leaves the intended permission undefined —
which itself fails silently at runtime (Finding 8). SpiceDB rejects duplicate permission names at
compile time.

**Fix:** mirror `extract-relations`: reduce into a map keyed by permission name and throw
`:eacl.schema/duplicate-permission` on collision. (The relation/permission name-collision check in
`extract-definitions` already exists; this closes the remaining hole.)

## 3. [Medium] `read-relationships` required-filter contract is not enforced

**Where:** [impl.clj:407-427](../../src/eacl/datomic/impl.clj) and
[core.clj:313-335](../../src/eacl/datomic/core.clj) (`spiceomic-read-relationships`).

The protocol docstring ([eacl/core.clj:27-34](../../src/eacl/core.clj)) says *"one of
`:resource/type`, `:subject/type` or `:resource/relation` is required"*. Nothing enforces it, at
either layer.

**Verified:** `(impl/read-relationships db {})` returns the entire relationship index (16/16 rows in
the test db) via the `:global-reverse` plan with an empty tuple prefix — a full AVET scan of every
relationship in the database, paged at 1000.

Two consequences:

- A typo'd filter key (`:subject-type` instead of `:subject/type`) degrades to the same global scan
  and **returns rows the caller did not intend to expose**. For an authorization library this is the
  dangerous direction to fail in — the 2026-07-06 audit fixed exactly this failure shape for
  unresolvable ids (finding 4); unknown/absent filter *keys* deserve the same treatment.
- Even a legitimate single filter (`:resource/relation` only, when that name exists on several
  type pairs) silently falls back to the unbounded scan with post-filtering.

**Fix:** validate in `spiceomic-read-relationships` (and/or `impl/read-relationships`): require at
least one of the three documented anchors, and reject unknown filter keys the way `make-client`
rejects unknown options (`:eacl/invalid-config` precedent). If the unbounded enumeration is a
feature you want to keep, gate it behind an explicit `{:allow-full-scan? true}`.

## 4. [Medium] `:resource/id-prefix` is documented but silently ignored

**Where:** declared in the protocol docstring ([eacl/core.clj:32](../../src/eacl/core.clj));
no implementation anywhere — `relationship-matches-filters?`
([impl.clj:214-225](../../src/eacl/datomic/impl.clj)) has no prefix clause.

**Verified:** `{:resource/type :server :resource/id-prefix "s1"}` returns exactly the same 12 rows
as without the prefix — a caller filtering by prefix silently receives unfiltered data.

**Fix:** either implement it at the Spiceomic layer (prefix-match against *external* string ids
after `entid->object-id` coercion — it cannot work at the impl layer where ids are eids), or remove
it from the protocol docs. Until then it is a silent no-op filter, same failure class as Finding 3.

## 5. [Low] `validate-schema-references` builds malformed error maps

**Where:** [schema.clj:296-320](../../src/eacl/datomic/schema.clj) — three of the five error
constructors close the `(str …)` too early, so the tail of the message becomes a stray
string-keyed map entry:

```clojure
{:type    :invalid-self-relation
 :message (str "Permission " (name res-type) "/" (name perm-name))   ; ← paren closes here
          " references non-existent relation: " (name target-name)}  ; ← stray key/value pair
```

**Verified output:**

```clojure
{:type :invalid-self-relation, :permission "doc/view", :target :owner,
 :message "Permission doc/view",
 " references non-existent relation: " "owner"}   ; ← stray entry
```

Affected: `:invalid-self-relation` (296-301), `:invalid-self-permission` (303-309),
`:missing-source-relation` (314-320). The two arrow-target constructors (330-349) are correct.
Impact is cosmetic-but-embarrassing: truncated messages in exactly the errors users hit while
debugging schemas, plus junk keys for anything that serializes `ex-data`.

**Fix:** move the closing paren; add a test asserting the full message and that every error map's
keys are keywords.

## 6. [Low] `rule-id` typo in `compile-recursive-rules`

**Where:** [indexed.clj:665-667](../../src/eacl/datomic/impl/indexed.clj):

```clojure
{:id (rule-id node :arrow-relation path [(:subject-type sub-path
                                                        (:relation-eid sub-path))])
```

That is `(get sub-path :subject-type <default>)` — one id segment, not the intended two
`[(:subject-type sub-path) (:relation-eid sub-path)]`.

**Verified shape:** `[:arrow-relation [:folder :view] :parent :folder 17592186045419 :user]` — the
`relation-eid` segment is missing (the `:user` is the subject-type; the default is never used
because `:subject-type` is always present).

**Why it doesn't bite today:** within one path, `sub-paths` come from `relation-datoms` on a unique
tuple, so subject-types are distinct per path, and `rule-id` already includes `via-relation-eid` —
so no two live rules collide. It is a landmine for any future schema shape where sub-path identity
needs the relation eid (and rule ids feed both sorting and consumer ordering, i.e. cursor-ordinal
determinism).

**Fix:** `[(:subject-type sub-path) (:relation-eid sub-path)]`. No behavior change expected;
recursive cursor ordinals for existing data are unaffected only if rule *sort order* is unchanged —
in the common single-sub-path case it is. Land it together with a note that outstanding recursive
cursors (5-minute TTL) may be invalidated, which the stale-cursor machinery handles loudly.

## 7. [Low] Raw-impl sharp edges: string ids throw; `:exhausted` needs a fixed basis

Two related hazards for callers using `eacl.datomic.impl.indexed` directly (the README explicitly
invites this for performance):

- **String ids throw raw Datomic errors.** `can?`, `lazy-merged-lookup`, and both recursive pages
  call `(d/entid db (:id subject))`. `d/entid` on a plain string throws
  `IllegalArgumentExceptionInfo` (verified), it does not return nil — so
  `(idx/can? db (spice-object :user "user-1") …)` explodes with a Datomic error instead of EACL's
  `:eacl/unknown-object` convention or `false`. Lookup refs and eids are fine. Recommend a
  `resolve-object-eid` helper that maps strings through `[:eacl/id s]`, or at minimum wraps the
  failure in `ex-info` naming the offending object.
- **`:exhausted` frontiers are only sound at a fixed basis.** The public token layer pins
  `d/as-of basis-t`, so this is safe through `Spiceomic`. A raw-impl caller who holds a cursor map
  and re-derives `(d/db conn)` between pages will have `:exhausted` paths **silently skip
  relationships written after the first page** — no error, just missing rows. Worth an explicit
  warning in the README's "call the internals directly" paragraph and in the
  `lazy-merged-lookup`/`frontier-permission-paths` docstrings.

## 8. [Low] Unknown permission / subject-type names fail silently

`lookup-resources`/`lookup-subjects`/`can?` with a typo'd `:permission` return empty/false: the
permission resolves to zero paths and evaluation proceeds. Similarly, `lookup-subjects` with a
`:subject/type` that matches no relation's subject type returns empty (in the recursive reverse
engine the type filter at [indexed.clj:1072](../../src/eacl/datomic/impl/indexed.clj) simply never
matches). SpiceDB fails these with `FAILED_PRECONDITION` so typos surface in development instead of
as "nobody has access". Since schema is already cached per basis, a cheap
`(seq (find-permission-defs db type permission))` guard with a
`:eacl.schema/unknown-permission` error would close this without measurable cost.

## 9. [Low] `:consistency` handling is inconsistent across the surface

`spiceomic-can?` throws unless `consistency/fully-consistent` ([core.clj:371-376](../../src/eacl/datomic/core.clj));
`lookup-resources`, `lookup-subjects`, `read-relationships`, `count-resources` ignore the key
entirely. Two side effects:

- Passing `(consistency/fresh token)` to a lookup silently does nothing rather than throwing like
  `can?` does.
- `:consistency` is *not* stripped by `list-query-shape`, so including it on page 1 but not page 2
  yields "Page token does not match the current query" — technically correct, practically baffling.

**Fix:** validate consistency uniformly (reject non-fully-consistent everywhere), and either
dissoc it from the query-shape hash or document that every non-pagination key is part of token
identity.

## 10. [Low] Dead code & doc drift

- [core.clj:168-196](../../src/eacl/datomic/core.clj): `default-internal-cursor->spice` /
  `default-spice-cursor->internal` handle a `{:v 2 :e … :p …}` cursor shape that no longer exists;
  no callers in src or tests. Delete (they misleadingly suggest cursors leave the peer decrypted).
- [base.clj:4](../../src/eacl/datomic/impl/base.clj): `(defrecord Cursor [path-index resource])` —
  v6-era, unused.
- [impl/spicedb.clj](../../src/eacl/impl/spicedb.clj): empty stub ns with a stale `eacl.protocols`
  reference in a comment.
- [parser.clj:275-289](../../src/eacl/spicedb/parser.clj): `analyze-definition` filters a *map* of
  definitions with `(:name %)` on map entries — always returns nil. Dev helper, but it's exported
  and documented by example; fix the destructuring or drop it.
- `count-subjects` exists and is correct in [indexed.clj:1754](../../src/eacl/datomic/impl/indexed.clj)
  but is not on the protocol and not reachable from `Spiceomic` (`count-resources` is). Expose it or
  note it as impl-only.

## 11. [Info] `assert-storage-compatible!` accepts future stamps

[v6_to_v7.clj:384-386](../../src/eacl/migrations/v6_to_v7.clj): the guard passes for any
`stamp >= 7`. If a hypothetical v8 migration re-shapes relationship storage and stamps `8`, today's
v7 code will happily start against it — the exact silent-empty failure the guard exists to prevent,
one major version later. Cheap insurance: refuse `stamp > storage-version` with the same
`:eacl/storage-version` error.

## Performance & design observations (not bugs)

- **Frontier pruning depends on eid correlation.** In the adversarial scenario (account created
  *before* the servers it grants, mapping to the *highest* server eids), the frontier legitimately
  stays pinned at the first intermediate for the whole walk — every page still probes every
  intermediate from the frontier onward. Correct, but the `calls-by-page`-decreasing behavior the
  bench asserts only materializes when intermediate order roughly tracks result order (the common
  case, since related entities are created together). Worst-case page cost remains
  O(intermediates ≥ frontier) index probes per arrow path.
- **Every arrow path pays an eager frontier probe per page** — `arrow-via-intermediates` forces
  `(first pairs)` when the path result map is built, even if the page fills entirely from another
  path. Bounded by "intermediates until first contributor", and pre-7.3 code had the same cost via
  `min-int`, so nothing regressed; just know it's eager, not lazy.
- **Recursive `count-resources` is O(n²/page)** — each 10k page replays the traversal from scratch
  in `:seek` mode. Fine under the current 100k `*recursive-traversal-limits*`; revisit if limits
  are raised.
- **`write-schema!` orphan check is read-then-write.** `count-relationships-using-relation` runs on
  the pre-transaction db; a relationship created concurrently on a relation being retracted slips
  through and is orphaned. A transaction function performing the count inside the tx would make
  retraction atomic; today's window is small and the failure is "dead datoms", not wrong grants.
- **`d/with` speculative dbs share the plain cache scope** (`classified-view` → `:plain`, same
  `(.id db)`), which is correct *under the documented write-schema!-only contract* — a speculative
  `write-schema!`-shaped tx carries its own new squuid and lands in its own cache slot. Worth a
  line in the `classified-view` docstring so nobody "fixes" it.
- **Page-token TTL (default 300s) bounds UI paging sessions.** Documented in the README; surfacing
  the remaining TTL (or a `:page-info :expires-at`) would let long exports refresh proactively
  instead of dying on "Expired page token."

## Test recommendations

1. Parser round-trips for keyword-prefixed identifiers (Finding 1 list) — the parser tests
   currently have no adversarial identifier coverage.
2. Duplicate-permission rejection (Finding 2), alongside the existing duplicate-relation test.
3. `read-relationships` filter validation: `{}`, typo'd keys, and `:resource/id-prefix` behavior,
   whichever way Findings 3/4 are resolved.
4. Promote the anti-correlated eid-ordering setup used in this review into
   `differential_test` — its random fixtures naturally correlate creation order with eid order, so
   the frontier's worst case (pinned frontier, zero pruning) currently has no differential
   coverage.
5. An assertion that every `validate-schema-references` error map contains only keyword keys and a
   complete `:message` (Finding 5).
