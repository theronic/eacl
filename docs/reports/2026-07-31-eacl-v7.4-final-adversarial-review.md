# EACL v7.4 final-head adversarial correctness and performance review

**Date:** 2026-07-31  
**Reviewed branch:** `codex/intelligent-eacl-cache`  
**Reviewed committed head:** `5054da1539e42cd4be1ed117711eb05aee2e236d`  
**Local `main` used for comparison:** `5e9206262ef2a4b247e355011cf570684bc38e77`  
**Pull request:** [theronic/eacl#80](https://github.com/theronic/eacl/pull/80)  
**Status of this document:** current follow-up review of the final prospective v7.4 head plus the
uncommitted fixes described below

## Verdict

The committed PR head was **not safe to ship**.

The most serious failures were not cosmetic cache defects:

1. two concurrent schema replacements could both commit and leave the database with the **union**
   of two proposed schemas;
2. relation removal had a read/check/write race that could strand a relationship under a removed
   relation;
3. a relationship transaction prepared under an old schema could commit after relation removal;
4. two concurrent `:create` operations for the same relationship could both report success, in
   direct violation of the public operation contract; and
5. `delete-object!` advertised bounded batching while retaining the entire high-degree deletion in
   memory before the first batch was submitted.

Those defects are fixed in the accompanying worktree changes and covered by deterministic
regressions. The final fresh non-benchmark suite passes **220 tests / 10,138 assertions**, with zero
failures and zero errors. The heavy pagination/load suite separately passes **7 tests / 3,301
assertions**, also with zero failures and zero errors.

With these fixes, the cache's central coherence model is technically sound under its stated write
contract: EACL relationship helpers atomically advance per-relation stamps, result entries record
their relation dependencies, and readers validate those stamps from Datomic rather than relying on
process-local invalidation messages.

That is not the same as saying the library is impossible to misuse. Three production constraints
remain severe:

- raw writes to EACL tuple attributes bypass relation stamps and can make exact cached answers
  stale;
- a client deliberately latches one schema generation and must be recreated after an out-of-band
  schema write; and
- multi-batch object cleanup is not a linearizable object-deletion protocol in the presence of
  concurrent relationship creation.

These are documented design boundaries, not bugs silently hidden by this report. They need explicit
production policy.

**Overall confidence:** high for the confirmed findings and fixes; moderate for absolute
performance conclusions outside the in-memory benchmark environment; unknown for production
workloads that bypass EACL's mutation helpers.

## Relationship to the earlier 2026-07-31 report

`docs/reports/2026-07-31-eacl-v7.4-cache-adversarial-review.md` reviewed an intermediate cache
architecture. Several options and mechanisms discussed there no longer exist at the final head,
including boolean client cache configuration and `:live-results?`.

That report remains useful as history, but it is not a reliable description of the final API or
implementation. In particular:

- client `:cache` now takes an adapter, an adapter configuration map, `nil`/omission for the default
  local adapter, or `eacl.datomic.cache/no-cache`;
- request `:cache? false` bypasses the configured cache for one operation;
- boolean client values are rejected;
- invalidation is per relation rather than process-coordinated; and
- exact-answer retention defaults to `:on-repeat`.

This document is the authoritative review for committed head `5054da1` plus the fixes in the
current worktree.

## Detailed findings and fixes

## C1 — concurrent schema replacement was not a replacement

**Severity:** Critical  
**Confidence:** High  
**Affected code:** `eacl.datomic.schema/write-schema!`

### Original behavior

`write-schema!`:

1. read a Datomic value;
2. read the current EACL schema;
3. calculated additions and retractions in the application process; and
4. submitted ordinary add/retract operations.

Two callers starting from schema generation `G0` could therefore compute independent diffs and both
commit:

```text
G0
├── writer A computes “add :left”
└── writer B computes “add :right”

commit A → {:left}
commit B → {:left, :right}
```

The result was not either proposed replacement. It was their union. Worse,
`:eacl/schema-string` could contain only the last writer's text while the relation and permission
entities represented both writers.

This violates the strongest invariant of the schema API: one successful replacement must publish
one complete schema generation.

### Fix

Every schema transaction now includes `:db.fn/cas` on `:eacl/schema-version` in the same
transaction as:

- relation additions/retractions;
- permission additions/retractions;
- the stored schema string; and
- the next schema version.

The compare value is the generation against which the diff was calculated. One structural writer
wins. The other receives typed `:eacl.schema/concurrent-write`.

A structural no-op uses CAS with old and new equal. That is deliberate: it still checks that no
structural writer committed after the diff was calculated.

### Verification

`concurrent-schema-replacements-do-not-merge-test` forces both writers to reach transaction
submission together. It asserts:

- exactly one result is `:ok`;
- exactly one result is `:eacl.schema/concurrent-write`; and
- the database contains either `#{:left}` or `#{:right}`, never their union.

This is deterministic interposition, not a probabilistic loop.

## C2 — relation removal could race relationship creation

**Severity:** Critical  
**Confidence:** High  
**Affected code:** `eacl.datomic.schema/write-schema!`,
`eacl.datomic.impl/tx-relationship`, `tx-update-relationship`

### Original behavior

The orphan check counted relationship tuples in an application-side immutable database value, then
submitted relation retraction later.

The following history was legal:

```text
schema writer: count relation R → 0
relationship writer: commit a relationship using R
schema writer: retract relation R
```

The relationship tuple values retain the old relation eid, but the relation definition is gone.
The grant becomes unreachable to normal traversal and cannot be manipulated through the normal
schema-resolved relationship API.

A second history was also possible:

```text
relationship writer: resolve R and prepare tuple tx from schema G1
schema writer: remove R and commit schema G2
relationship writer: commit the delayed G1 tuple tx
```

The delayed mutation could reintroduce data under an obsolete relation eid.

### Fix

There are two complementary guards.

First, relation removal invokes a Datomic transaction function,
`:eacl.fn/assert-relation-unused`, inside the same transaction that retracts the relation. The
function probes both tuple indexes:

- the normal forward half; and
- the reverse half, so a pre-existing one-sided corrupt relationship also prevents removal.

It throws typed `:eacl.schema/relation-in-use`.

Second, low-level relationship tx-data carries a schema-generation CAS asserting that the schema
version used to resolve the relation is still current at commit. The public mutation path
deduplicates this guard and retries safe CAS contention against a fresh database value.

### Verification

The regressions cover three distinct cases:

1. `relation-removal-is-checked-again-at-commit-test` injects a relationship after the preflight
   count but before schema transaction submission and verifies typed rejection.
2. `stale-relationship-tx-cannot-resurrect-a-removed-relation-test` prepares relationship tx-data,
   removes the relation, then verifies the stale tx fails with `:db.error/cas-failed`.
3. `relation-removal-rejects-reverse-only-orphans-test` manually removes the forward half and
   verifies the transactor guard still sees the reverse half.

The ordinary preflight count remains useful because it reports a count without paying for a doomed
schema transaction. It now also returns the same stable relation-in-use type as the commit-time
guard.

## H1 — duplicate concurrent `:create` violated the public contract

**Severity:** High  
**Confidence:** High  
**Affected code:** `eacl.datomic.core/spiceomic-write-relationships!`,
`eacl.datomic.impl/tx-update-relationship`

### Original behavior

`:create` checked relationship absence against an immutable database value. Two callers could both
observe absence. Datomic cardinality-many additions of the same value are idempotent, so both
transactions could commit and both API calls could return success.

The stored data ended up valid, but the operation contract was false. A caller using `:create` for
duplicate detection could not trust the result under concurrency.

### Fix

Public relationship mutation now converts ordinary per-relation version stamps into
per-relation CAS operations:

```clojure
[:db.fn/cas relation-eid
 :eacl/relation-version
 observed-version
 "datomic.tx"]
```

Mutations affecting the same relation serialize on that relation's version. A loser rebuilds from
a fresh database value:

- a duplicate `:create` now observes the winner and returns
  `:eacl/relationship-conflict`;
- independent mutations using the same relation retry safely; and
- a relation removed during retry fails closed as `:eacl/schema-changed`.

Retries are bounded at eight attempts. Exhaustion throws typed
`:eacl/relationship-contention`, rather than looping forever.

### Verification

`concurrent-create-preserves-conflict-semantics-test` forces two clients to submit against the same
initial relation version. The exact result set must be:

```clojure
#{:ok :eacl/relationship-conflict}
```

## H2 — `delete-object!` batching was cosmetic

**Severity:** High for high-degree objects; performance/availability  
**Confidence:** High  
**Affected code:** `eacl.datomic.impl/tx-delete-object`,
`eacl.datomic.core/spiceomic-delete-object!`

### Original behavior

The public function eventually partitioned transaction data into batches, but the low-level helper
first performed:

```clojure
(vec (distinct (concat ...all relationship retractions...)))
```

That retains:

- every emitted retraction;
- the complete `distinct` set; and
- the final vector

before the first transaction can begin.

The operation was transaction-batched but not discovery-bounded. For an entity with millions of
edges, this could exhaust heap before batching helped.

### Fix

`tx-delete-object-stream` now emits tuple retractions lazily and chooses a canonical discovery path
for healthy relationships:

- peer halves name the object and provide one canonical copy;
- own halves are used for one-sided corrupt data;
- a self-relationship is emitted exactly once; and
- no whole-result `distinct` set is needed.

The public function partitions this stream before realization. Each batch independently:

- derives its relation stamps;
- converts them to optimistic relation CAS operations;
- carries the schema-generation guard; and
- retries bounded contention.

`tx-delete-object` remains as a materialized compatibility helper for callers that explicitly want
one transaction.

### Verification

- `delete-object-discovery-is-lazy-and-nonduplicating-test` verifies that 20 relationships produce
  a non-vector stream of exactly 40 tuple retractions.
- `delete-object-stream-handles-self-relationships-once-test` verifies a self-edge produces exactly
  two tuple retractions and is removed once.
- Existing multi-batch tests verify actual committed retraction counts.
- An in-memory smoke run created 1,000 relationships and deleted the subject in about 16 ms,
  reporting exactly 2,000 committed tuple retractions and zero remaining relationships. This is a
  functional load smoke result, not a portable latency guarantee.

## H3 — missing relation filters caused global scans

**Severity:** High on large relationship stores; performance  
**Confidence:** High  
**Affected code:** `eacl.datomic.impl/relationship-page`

### Original behavior

A valid query such as:

```clojure
{:resource/relation :does-not-exist
 :first 10}
```

resolved to an empty relation-definition set. Instead of proving the answer empty, the generic
plan scanned the global relationship tuple index and rejected every datom because none had a
matching relation eid.

The cost was proportional to the entire relationship store for a result known to be empty before
the scan.

### Fix

After normal bound validation, an empty relation-eid set returns an empty page immediately with nil
cursors and both page-direction flags false.

### Verification

`missing-relation-filter-does-not-scan-relationship-tuples-test` instruments
`datomic.api/seek-datoms` and asserts zero seeks.

## M1 — invalid schema input could mutate the database before rejection

**Severity:** Medium  
**Confidence:** High  
**Affected code:** `eacl.datomic.schema/write-schema!`

### Original behavior

The v7.4 compatibility installer transacted missing schema/cache support attributes before parsing
and validating the proposed schema. A malformed or reference-invalid schema correctly failed, but
the database had already changed.

That contradicted ADR 012's explicit contract: invalid schema causes no database changes.

### Fix

Parsing, transformation and reference validation now precede compatibility installation.

On a valid write, `write-schema!` installs any missing:

- `:eacl/schema-version`;
- `:eacl/relation-version`; and
- `:eacl.fn/assert-relation-unused`.

### Verification

`invalid-schema-does-not-install-cache-stamp-attributes-test` starts from a database missing all
three, submits a reference-invalid schema, and verifies all three remain absent.

## M2 — explicit `:cache? true` split exact-answer identities

**Severity:** Medium; performance  
**Confidence:** High  
**Affected code:** lookup and count query identity construction in
`eacl.datomic.core`

### Original behavior

Omitting `:cache?` and explicitly supplying `:cache? true` have identical semantics. Cursor
identity already excluded the option, but finished lookup and count cache keys retained it in an
internal query map.

The equivalent calls therefore populated separate exact-answer entries and recomputed traversal.

### Fix

`:cache?` is removed from internal lookup-page and count query identities. `:cache? false` still
bypasses all reads and publications before key use.

### Verification

`explicit-cache-true-does-not-fragment-answer-keys-test` instruments the indexed lookup/count
functions. Omitted then explicit-true calls invoke each underlying computation exactly once.

## M3 — encoder could mint an undecodable page token

**Severity:** Medium; availability/usability  
**Confidence:** High  
**Affected code:** `eacl.datomic.core/encrypt-page-token`

### Original behavior

The decoder rejected encoded tokens longer than 16,384 characters. The encoder imposed no
corresponding output limit.

A sufficiently large recursive frontier or payload could therefore produce a successful first
response containing a continuation cursor that the next request necessarily rejected.

### Fix

The encoder checks final encoded length and throws typed
`:eacl.pagination/cursor-too-large`, including actual and maximum lengths.

This moves failure to the response that attempted to create an unusable cursor and gives operators
a stable diagnostic.

### Verification

`page-token-encoder-never-mints-a-token-its-decoder-refuses-test` uses a 20,000-character payload
and asserts the typed error and length relation.

## M4 — page-token TTL validation was incomplete

**Severity:** Medium; usability and numeric safety  
**Confidence:** High  
**Affected code:** `eacl.datomic.core/make-client`, `page-token`

### Original behavior

Invalid TTLs did not fail consistently:

- a string leaked a raw numeric/class exception;
- zero and negative values could be diagnosed through an unrelated cache TTL path;
- extremely large integers could overflow later millisecond arithmetic; and
- the error key could point at `:ttl-ms` instead of `:page-token-ttl-seconds`.

### Fix

The client boundary and token boundary now require a positive integer no greater than:

```clojure
(quot Long/MAX_VALUE 1000)
```

That bound keeps both second expiry and cache millisecond lifetime safely representable. Rejection
is typed `:eacl/invalid-config` with key `:page-token-ttl-seconds`.

### Verification

The regression rejects `nil`, `"300"`, `0`, `-1`, and one above the maximum.

## M5 — stale repair tx-data could resurrect a removed relation shell

**Severity:** Medium  
**Confidence:** High  
**Affected code:** `eacl.datomic.integrity/repair-tx-batches`

### Original behavior

Integrity repair correctly paired every dangling-half retraction with a relation-version stamp.
However, a batch could be prepared, committed once, followed by relation removal, and then
accidentally resubmitted.

The retraction would be a no-op, but the ordinary stamp could recreate the old numeric relation eid
with only `:eacl/relation-version`. It would not restore the schema definition, but it would leave a
misleading shell entity and violate the expectation that a removed relation stays removed.

### Fix

Every official repair batch now carries the source database's schema-generation CAS. A stale batch
fails atomically before either its retraction or stamp can commit.

### Verification

`public-integrity-audit-is-explicit-and-bounded-test`:

1. constructs an orphan;
2. captures a repair batch;
3. commits it;
4. removes the now-unused relation;
5. resubmits the stale batch;
6. observes `:db.error/cas-failed`; and
7. verifies the removed eid did not regain a version stamp.

## L1 — page-token envelope accepted unauthenticated suffixes

**Severity:** Low–Medium  
**Confidence:** High  
**Affected code:** `eacl.datomic.core/decrypt-page-token`

### Original behavior

The binary envelope contains a declared ciphertext length. The decoder read and authenticated
exactly those bytes but did not require end-of-input.

An attacker could append arbitrary bytes to an otherwise valid token, re-encode it, and have the
token accepted. The suffix did not change authorization semantics, so this was not an authorization
bypass. It was nevertheless non-canonical parsing of attacker-controlled unauthenticated data.

### Fix

The decoder rejects any remaining envelope byte after reading the declared ciphertext.

### Verification

`page-token-envelope-rejects-unauthenticated-trailing-bytes-test` appends a byte to a valid binary
envelope and expects the public invalid-cursor error.

## L2 — inner codec was non-canonical and leaked range exceptions

**Severity:** Low–Medium  
**Confidence:** High  
**Affected code:** `eacl.datomic.codec`

### Original behavior

Two boundary problems existed:

1. `decode` returned the first value and ignored remaining plaintext bytes.
2. Encoding an integer outside signed 64-bit range relied on `long`, leaking a raw
   `IllegalArgumentException` rather than the codec's typed rejection.

The second behavior did not silently wrap on the Clojure/JVM version tested; it threw. The bug was
the unstable exception boundary, not numeric corruption.

### Fix

- `decode` now requires end-of-input and throws `:eacl.codec/malformed` for a suffix.
- integer encoding explicitly checks `Long/MIN_VALUE <= value <= Long/MAX_VALUE` and throws
  `:eacl.codec/unencodable` outside the wire range.

### Verification

Dedicated regressions cover trailing input and both out-of-range directions.

## L3 — schema adoption read two database values

**Severity:** Low; performance/hygiene  
**Confidence:** High for the redundant/torn reads, low that current code produced a wrong
authorization answer by this mechanism alone  
**Affected code:** `eacl.datomic.core/adopt-schema-generation!`

### Original behavior

An unstamped client adoption path read:

1. a database value to discover the schema version before taking the client lock; and
2. another database value to construct the cache-generation object after taking the lock.

That was a redundant `d/db` call and an avoidable torn-snapshot boundary.

The current `make-schema-cache` does not eagerly compile permission paths, so it would be
inaccurate to claim this alone paired V1's UUID with V2's compiled paths. The defect was weaker:
the code established an unsafe boundary for future eager generation state and paid a needless read.

### Fix

The write lock is acquired first, then one immutable database value supplies both version and
generation construction.

### Verification

`schema-generation-adoption-uses-one-database-value-test` interposes two database values and asserts
one call and matching generation labels.

## Cache correctness analysis

## What is now sound

### Per-relation invalidation

Each relation entity has a cardinality-one, `:db/noHistory` `:eacl/relation-version` ref. EACL
relationship mutations publish the current transaction entity as the new value.

The important properties are:

- transaction entity ids increase monotonically with Datomic `t`;
- all tuple mutations and their stamp commit atomically;
- multiple mutations of one relation in one transaction collapse to one stamp;
- cached answers store the set of relations traversed; and
- the reader takes the maximum current stamp over exactly that dependency set.

An unrelated relation write does not invalidate the entry. A related relation write necessarily
changes the dependency generation. There is no process-local invalidation race and no coordinator
to partition across instances.

**Confidence:** High under helper-mediated writes.

### Historical consistency

For stale-tolerant and exact-snapshot reads, the answer and cursor carry an authenticated historical
basis. EIDs in cached results are resolved against the answer's own historical database value,
avoiding the error where a later live deletion makes an old answer impossible to externalize.

When a continuation is absent, the implementation reconstructs the authenticated historical basis
and deterministically replays the prefix. Cache eviction is therefore a performance event, not a
semantic change.

**Confidence:** High, supported by consistency, cache differential, recursive, watermark and
schema-basis suites.

### Cache failure containment

Provider lookup, publication, capability, metric and cleanup failures are contained as misses,
rejected publications or best-effort telemetry. They do not replace the authoritative result.

The explicit `no-cache` adapter runs the same authorization logic without caching.

**Confidence:** High for tested provider failures.

## What is deliberately not guaranteed

### Raw tuple writes

If application code directly writes:

- `:eacl.v7.relationship/subject-type+relation+resource-type+resource`; or
- `:eacl.v7.relationship/resource-type+relation+subject-type+subject`

without using EACL tx-data helpers, it also bypasses `:eacl/relation-version`. Exact cached answers
can remain stale until TTL.

No in-process cache design can discover such a write without observing a broader Datomic
generation and sacrificing the per-relation benefit.

**Residual severity:** High  
**Confidence:** High

Recommendation: prohibit direct tuple writes in production code review and expose only a narrow
mutation module. If direct transactions are unavoidable, require
`stamp-relation-versions`/the optimistic helper in the same transaction.

### Out-of-band schema writes and long-lived clients

A client captures a schema generation. `write-schema!` through that client rotates its state after
success. A different client or process can change schema, leaving the old client outdated.

`eacl.datomic.integrity/client-schema-status` detects this explicitly, but hot authorization reads
do not poll the schema version.

**Residual severity:** High operationally  
**Confidence:** High

Recommendation: make schema deployment an operational barrier:

1. stop or drain authorization instances;
2. write schema once;
3. recreate all clients; and
4. reject readiness until `client-schema-status` is `:current`.

A future implementation could compare the schema version from the already-selected request DB
value, but the extra indexed read must be benchmarked before putting it on every hot path.

## Performance analysis

## Heavy suite results

The heavy namespace was run separately because it is intentionally excluded from the normal suite.
The measured environment is an in-memory Datomic database in the existing warmed development JVM.
These numbers are regression evidence, not production capacity promises.

### 15,000-resource fixture

Fixture: 30 accounts × 500 servers, 4 teams/account, 2 VPCs/account.

| Measurement | Result |
|---|---:|
| First page, `:first 50`, median | 2.05 ms |
| First page p95 | 4.14 ms |
| Forward pagination, early pages | 0.90 ms/page |
| Forward pagination, late pages | 0.81 ms/page |
| Reverse pagination, early pages | 1.30 ms/page |
| Reverse pagination, late pages | 1.22 ms/page |
| Resource count cold | 20.34 ms |
| Resource count exact-cache hit | 0.031 ms |
| Resource count cache disabled | 19.93 ms |
| `can?` warm | 21.38 µs |
| `can?` cold path | 116.44 µs |
| `can?` completed-answer hit | 9.88 µs |

Late page latency did not grow with offset. That is the central pagination performance property.

### Recursive scaling

At a chain length of 4,000 over 160 pages:

| Strategy | Work units | Time |
|---|---:|---:|
| retained continuation | 4,159 | 32.97 ms |
| prefix replay | 322,159 | 1,538.01 ms |

That is:

- **77.46× less traversal work**; and
- **46.65× lower measured time**.

The difference between those ratios is expected: fixed token, boundary coercion, cache and test
instrumentation costs remain even as traversal work collapses.

### Broad counts

The broad-count scenarios each returned 20,000 results while retaining at most 16,384 EIDs in a
page, including:

- cache disabled;
- cache admission rejected; and
- provider publication failure.

This verifies the bounded fallback path, not merely the happy cache-admitted path.

## Performance conclusions

1. **Continuation caching is justified.** It changes recursive pagination from repeated prefix work
   to near-linear total work.
2. **Exact answer retention is useful when calls repeat.** A completed `can?` hit was about 2.2×
   faster than the warm non-completed path in this run.
3. **The count cache has a large payoff for repeated broad counts.** The measured resource-count
   hit was roughly 650× faster than the cold computation.
4. **A missing relation must short-circuit.** The fixed path performs zero index seeks instead of
   work proportional to all relationships.
5. **Object-deletion discovery must remain lazy.** Transaction batch size is meaningless if
   discovery first retains the whole result.

## Performance risks still present

### One monitor in the default local LRU

The built-in `LocalStore` uses one access-ordered `LinkedHashMap` guarded by one monitor. Access
ordering mutates the map on every hit, so a lock is required for that design.

Metrics were wisely moved outside the critical section, and prior work removed more expensive
process-local coordination. Nevertheless, all hits and stores on one local adapter serialize on
that monitor.

**Residual severity:** Low–Medium, workload dependent  
**Confidence:** High architecturally; moderate on materiality after the current improvements

Recommendation: retain the simple store as the default, but publish a concurrency benchmark and
make a striped or dedicated concurrent provider easy to plug in for high-core services. Do not
complicate the default until measurement shows the monitor dominating.

### Hot-relation write contention

Public relationship writes now serialize by relation version. This buys real linearizable
operation semantics, but one extremely hot relation definition can cause CAS retries even when
writers touch different endpoint pairs.

Eight immediate retries have no jitter or backoff.

**Residual severity:** Medium for write-heavy hot-relation workloads  
**Confidence:** High in mechanism; unknown in the author's production distributions

Recommendation:

- add a benchmark with 1, 2, 4, 8 and 16 writers against one relation and against many relations;
- record retry-count telemetry;
- consider bounded exponential backoff with jitter; and
- only consider a finer-grained uniqueness mechanism if measured contention is unacceptable.

Correct `:create` semantics are worth more than synthetic uncontended throughput.

## Remaining usability hazards

### Unknown request keys

`make-client` rejects unknown configuration keys and `read-relationships` has a known-key
validator. The other query APIs are less uniformly strict.

A misspelled filter can be worse than an exception: it can broaden a lookup, change work, or create
a different cache key.

**Residual severity:** Medium  
**Confidence:** Moderate; each public query shape should be catalogued before tightening

Recommendation: define explicit key sets at every public map boundary and reject unknown keys with
one stable error type. Do this in a minor release only after checking downstream consumers for
metadata keys.

### Random page-token key by default

A random per-client key is safe for a single in-process client, but a cursor becomes unusable after
restart or on another instance.

This behavior is documented. It is still a production trap.

**Residual severity:** Medium operationally  
**Confidence:** High

Recommendation: production integration docs should treat explicit keyring configuration as
mandatory for rolling deploys or load-balanced services, and should show key rotation with old-key
acceptance.

### Multi-batch object cleanup is not object lifecycle serialization

`delete-object!` removes relationships visible in its source database and does so in bounded
batches. A concurrent writer can create another relationship after discovery. The function also
intentionally does not retract or tombstone the application entity.

Therefore it means “clean the relationships I can discover,” not “atomically make this object
forever unable to participate in a relationship.”

**Residual severity:** High if consumers mistake it for a lifecycle primitive  
**Confidence:** High

Recommendation:

- document the distinction in the public docstring, not only README prose;
- for strict deletion, establish an application tombstone/state transition that relationship
  creation checks at commit;
- stop new writes, run cleanup, audit for dangling halves, then retract the entity; and
- use the single-transaction `tx-delete-object` plus `retractEntity` only when the degree is safely
  bounded.

## Ship recommendation

Do not ship commit `5054da1` without the accompanying fixes.

After the fixes, the candidate is suitable for a release candidate, not an unobserved production
rollout. Before final release:

1. run the full suite on the supported Datomic deployment mode, not only `datomic:mem`;
2. run a one-relation concurrent-write benchmark and record CAS retry distribution;
3. test the transaction function in the exact production transactor/runtime version;
4. run `dangling-relationship-report` on every production database before enabling exact answer
   retention;
5. enforce helper-only tuple mutation;
6. provide an explicit page-token keyring in every multi-instance deployment;
7. recreate clients as a schema-deployment barrier; and
8. define an object-deletion lifecycle that prevents new relationships during cleanup.

The strongest positive conclusion is narrow and important: with helper-mediated writes and one
stable schema generation per client, the final per-relation cache invalidation design is correct,
bounded, process-independent, and materially faster on repeated and recursive work.

The strongest negative conclusion is equally narrow: EACL still cannot make raw Datomic writes,
out-of-band schema deployment, or concurrent application object deletion safe by convention alone.
Production correctness depends on enforcing those boundaries.
